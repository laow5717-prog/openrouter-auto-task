# 轮转收敛改为跑到卡耗尽，零进展不再停

## Goal

充值任务当前会在「连续 2 轮零进展」时收敛，而**烧卡不算进展**——`gained` 只取新增
卡的差集。后果：只要一轮里没有任何账号付款成功，两轮后任务必停，卡池里还剩多少张
根本不参与判断。

2026-08-06 04:00 那次运行就是这么结束的：成功付款 0 次 / 未付成 28 次 /
**剩余可选卡 2596 张**（启动时 2773 张，只消耗了 177 张）。

用户要求：不要这个限制，跑到卡真正消耗完为止。

## Requirements

### R1 进展判据改为「卡集合是否变化」

- `src/web/app.py` `_try_claim` 的轮边界：
  `progressed = 付成过 or cards_now != cards_at_start`。
- **卡被烧掉（标 invalid / 进冷却而退出可选集）现在算进展**——这正是本任务要反转的
  那一条。只要每轮还在消耗卡，就一直开新一轮。
- 终止性由「可选卡集合有限且单调消耗」保证：卡耗尽后由既有的
  `分组可选卡已耗尽` 分支收敛。

### R2 保留空转护栏

- 唯一还会提前停的情况：连续 N 轮**既没付成、卡集合也一张没动**（既无新增也无减少）。
  那意味着流程根本没走到试卡环节（登录挂了 / 环境起不来 / hCaptcha 超时），再轮转只
  是原样重复，且永远到不了「卡耗尽」。
- 沿用现有阈值 2（容忍一轮瞬时抖动），提为具名常量。
- 计数器语义从「零进展」变为「完全空转」，改名 `idle_rounds` 并同步日志文案，
  否则日志会说「零进展」但实际每轮都在烧卡，与事实相反。

### R3 文档同步

- `run_daily_pipeline` docstring 的停止条件 2 要改：现在只有「完全空转」才停。
- 轮边界日志（`一轮轮转完毕仍有可选卡 N 张…`）的括注同步。
- `.trellis/spec/backend/concurrency-guidelines.md` 里记录该判据的段落同步更新，
  并保留 2026-08-05「113 轮不收敛」现场的历史说明——那个坑没有消失，只是现在由
  「卡耗尽」而非「零进展」来兜底，读者需要知道两者的区别。

## Non-goals

- 不动订阅任务（`run_daily_subscribe`）的判据。它本来就是「卡减少即算进展」
  (`after < remaining`)，已经符合本次要的语义，只是零容忍抖动；这次不改它。
- 不改卡的冷却/判无效规则本身。
- 不加「按卡种过滤 BIN」之类的选卡优化。

## 已知后果（用户已确认接受）

卡池全是被发卡行拒付的卡时，任务会把整个分组逐张烧成当日冷却后才停。2026-08-05
的现场（2 个账号反复失败、跑到第 113 轮、烧掉 630 张卡）在新判据下会跑得更久——
它现在是**预期行为**，不再是 bug。用户要的正是「不要限制，直到卡消耗完毕」。

## Acceptance Criteria

- [ ] 全失败但每轮都烧卡的场景：任务持续轮转直到可选卡耗尽才收敛，收敛原因是
      「分组可选卡已耗尽」而非「账号试尽」。
- [ ] 全失败且完全不动卡池的场景：仍在 2 轮后收敛，卡池原样未动
      （`test_zero_progress_two_rounds_then_stop` 的行为不变）。
- [ ] 混合场景：某轮烧了卡、下一轮完全空转 → 空转计数从 0 重新开始，不会因为
      前面几轮的历史提前停。
- [ ] 收敛日志与轮次日志不再出现「零进展」字样描述正在烧卡的轮次。
- [ ] 既有 542 项测试中，只有 `test_burning_cards_is_not_progress_so_it_still_converges`
      需要按新语义重写（它断言的正是本次要反转的行为），其余全绿。

## Notes

- 现场证据：`server.log:199346`「一轮轮转完毕仍有可选卡 2687 张，开始第 2 轮
  （重试 14 个上轮失败账号，上轮零进展）」→ 第 2 轮结束即收敛。
- 那批卡的拒付理由是 `club, unionpay / your card was declined`，属卡种问题；
  新判据下这类卡池会被整体烧进当日冷却。这是用户明确接受的代价。
