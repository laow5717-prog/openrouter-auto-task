# 失败卡冷却改为自然日边界，并发下不可绕过

## Goal

一张卡当日付款失败，当日就不再被选用，次日恢复；付款成功的卡不受限制，可反复使用。
并行 worker 下同一张卡当日也不得被刷第二次。

## Background

现状与目标的差距只在一条上，另两条已经满足：

| 目标 | 现状 | |
|---|---|---|
| 当日失败 → 当日不再用，次日恢复 | `set_cooldown(hours=24)` → `tds_until = now + 24h`，**滑动窗口** | ❌ |
| 并行 worker 不选到同一张卡 | `PaymentCardRegistry` 两级排他（`_in_flight` 全局 / `_used` 按平台按轮） | ⚠️ 有窗口 |
| 成功的卡可反复使用 | 成功标 `paid`、清 `fail_streak`、**不设冷却**，仍在可选集 | ✅ |

**滑动窗口的问题**：卡在 15:00 被拒要等到次日 15:00 才回来。发卡行的 velocity 风控
按自然日算，这个口径对不上，而且恢复时刻随失败时刻漂移，不可预期。

**并发窗口的位置**（`src/services/registration.py`）：`recharge_account` 在入口处
**一次性**过滤掉冷却中的卡（`cards = [c for c in payment_cards if not in_cooldown(...)]`），
之后整个会话都用这份快照逐张试卡。一次会话内连充多笔可能持续很久，期间另一个 worker
把某张卡刷失败并设了冷却，本会话的快照里它仍然在，照刷不误——同一张卡当日被刷两次。
`_in_flight` 挡不住（对方早已释放），`_used` 只覆盖同一轮。

这与 08-05 复用超充是同一类问题：判定用的是快照，而权威状态在判定之后发生了变化。

## Requirements

- R1 失败卡的冷却到期时刻改为 `max(次日 00:00, now + fail_cooldown_hours)`。
  取 max 而不是直接用次日零点：否则 23:59 失败的卡一分钟后就能再刷，
  当日限制形同虚设。
- R2 `config.yaml` 的 `fail_cooldown_hours` 保留，语义从「冷却时长」变为
  **「冷却时长下限」**，注释需同步改写。
- R3 付款**成功**的卡行为不变：不进冷却、清零连续失败计数、可反复使用。
- R4 并发下同一张卡当日不得被刷第二次：`recharge_account` 的试卡循环在
  `try_acquire` 成功之后、`top_up` 之前**实时复查冷却**，在冷却中则跳过该卡。
- R5 复查失败（DB 异常等）不得让整个会话中断，按「不在冷却」放行——安全网不能
  比它保护的流程更脆弱。
- R6 3DS 触发的冷却与充值失败的冷却共用同一套到期计算（都走 `set_cooldown`）。

## Non-Goals

- 不改 `max_fail_streak` 判废逻辑（连续失败达阈值判 invalid，与冷却是两件事）。
- 不改 `PaymentCardRegistry` 两级排他的语义（`_in_flight` 全局、`_used` 按平台按轮）。
- 不改 `_eligible_cards` 的排序（新卡优先、好卡复用）。
- 不改成功卡的任何行为。
- 不动 `try_acquire` 的准入判断——那里刻意只做并发排他，硬拦会让卡池偏紧时
  worker 拿不到卡而被误判成「卡池已耗尽」（见其 docstring）。

## Acceptance Criteria

- [ ] AC1 15:00 失败的卡，冷却到期时刻是**次日 00:00**，不是次日 15:00。
- [ ] AC2 23:59 失败的卡，冷却到期时刻是 `now + fail_cooldown_hours`
      （次日零点更早，被 max 取代），当日限制不被绕过。
- [ ] AC3 付款成功的卡不进冷却，同一会话内可被再次选用。
- [ ] AC4 会话入口快照之后、某张卡被别的 worker 刷失败并设冷却时，
      本会话跳过该卡而不是照刷（R4 的实时复查生效）。
- [ ] AC5 实时复查抛异常时该卡仍可被尝试，会话不中断。
- [ ] AC6 `fail_cooldown_hours` 仍从 config 生效，作为下限。
- [ ] AC7 `pytest tests/` 全量通过。
